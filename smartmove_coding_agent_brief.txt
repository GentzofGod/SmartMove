# Product Requirements and Implementation Brief
## Working title: SmartMove
### A local market intelligence, errand planning, and decision simulation app

## 1. Product vision

Build a mobile-first application that helps people make better everyday spending and time-management decisions. The app combines three capabilities into one coherent product:

1. **Community Market Intelligence:** Collect, organize, and compare local product price observations.
2. **Intelligent Errand Planner:** Build practical shopping and errand itineraries based on cost, location, time, opening hours, availability, and user priorities.
3. **Decision Rehearsal Engine:** Let users compare alternative plans under different budgets, transport costs, time limits, and other assumptions before choosing a plan.

The app should not feel like three unrelated tools placed in one interface. Price information feeds the planner, the planner creates candidate itineraries, and the decision engine compares those itineraries and explains their trade-offs.

The initial target context is local shopping and errands in Nigeria, but the architecture should allow other locations and currencies later.

**Core promise:** Help users decide what to buy, where to buy it, which errands to combine, and which practical plan best fits their budget and available time.

## 2. Hackathon context and principles

The product is intended for a Meta AI hackathon. Meta models must contribute meaningfully to the experience, rather than being included as decoration. Confirm the exact model names, API access, capabilities, pricing/credits, and usage limits against the current hackathon documentation before implementation.

The application must be honest about its data. At the beginning, we may not have access to live market prices. It is acceptable to build and demonstrate the product with simulated data if the interface clearly labels it as demo data. Never present invented prices, shop listings, stock availability, opening hours, or route estimates as verified real-world information.

Build a working, focused MVP first. Do not attempt to implement every future feature before the main workflow is complete.

## 3. Primary user scenario

A user says or enters:

“I have ₦15,000. I need rice, eggs, tomatoes, and cooking oil. I also need to collect a package before 2 PM. Help me plan everything.”

The application should:

1. Parse the request into a shopping list, quantities if provided, spending limit, deadline, and additional errand.
2. Show the available price observations and clearly identify whether each is simulated, community-reported, or trader-confirmed.
3. Generate feasible shopping and errand plans from available data.
4. Calculate item costs, transport costs, other configured expenses, number of stops, and estimated duration.
5. Compare candidate plans and explain the trade-offs.
6. Let the user change a constraint, such as the budget, transport fare, deadline, or preferred number of stops, and recalculate.
7. Let the user review and accept a plan, then mark errands complete as they go.

The app must never imply that the plan is guaranteed. Estimates and uncertain data must be visible to the user.

## 4. Intended users

- Individuals trying to manage limited budgets and daily errands.
- Households planning shopping trips.
- Students and workers who need to combine multiple tasks in limited time.
- Community members willing to contribute local price observations.
- Participating traders who want to maintain product and price information.

The MVP should focus primarily on the individual shopper. Trader tools and community-scale functionality can be introduced progressively.

## 5. Core product modules

### 5.1 Home: “Your next decision”

The home screen should prioritize actions, not be a dashboard full of charts. Show:
- A quick way to create a plan.
- Today's planned errands and deadlines.
- Saved shopping lists.
- A small selection of recent price changes for saved products, only when data exists.
- Remaining planned budget when relevant.
- Clear indicators when prices are simulated or stale.

Avoid empty, decorative metrics and unsupported claims.

### 5.2 Market: product and price discovery

Users can:
- Search and browse products.
- Compare reported prices across locations or sellers.
- View product unit/quantity, price, seller or source, location, report time, and verification status.
- Filter by distance/location, price, source type, and recency when the necessary data is available.
- See price history only where sufficient observations exist.
- Submit a new price observation.
- Report a stale or suspicious observation.

Data source labels must be explicit:
- **Demo data — simulated**
- **Community reported**
- **Trader provided**
- **Trader confirmed**
- **Independently verified** only if a real verification process exists.

Do not call a price “live” unless the app has a reliable live data source. Do not show a confidence score unless it is based on a defined, explainable method. Prefer simple labels such as “reported 2 hours ago” and “not recently verified.”

### 5.3 Errands: build a practical itinerary

Users can add:
- Shopping items and quantities.
- Non-shopping errands, such as collecting a package, visiting a service provider, or paying a bill.
- Destination/location, if known.
- Deadline or preferred time.
- Priority.
- Expected duration.
- Opening hours, if known.
- Constraints such as maximum travel time, maximum number of stops, or avoiding particular locations.

The planner should group compatible tasks and produce candidate itineraries. It should consider:
- Product availability in the current dataset.
- Shopping basket price.
- Travel/transport cost estimates.
- Travel time estimates.
- Opening-hour constraints.
- Errand deadlines and estimated service duration.
- Number of stops.
- User priorities.

Do not claim precise route optimization if no mapping/routing provider is connected. For the MVP, use manually entered travel times/fares or clearly labelled demo estimates. Design the routing interface so a mapping provider can be added later.

### 5.4 Decision Lab: compare scenarios

This is the signature feature. Let users compare two or more feasible plans side by side.

Scenario examples:
- Lowest estimated total cost.
- Lowest transport expense.
- Fewest stops.
- Shortest estimated duration.
- Stay within a strict budget.
- Complete all high-priority errands before a deadline.
- Delay selected non-urgent purchases, while making no unsupported prediction that prices will fall.

Users should be able to adjust assumptions such as:
- Total budget.
- Transport fares.
- Available time.
- Maximum number of stops.
- Product quantities or items.
- Preferred priorities.
- Deadline.
- Optional cost of time, if the user chooses to assign one.

For every plan, show:
- Estimated product cost.
- Estimated transport cost.
- Other configured expenses.
- Total estimated cost.
- Estimated duration.
- Number of stops.
- Which constraints are satisfied or violated.
- Missing, stale, or simulated data affecting the result.
- Why the plan is recommended and what trade-offs it makes.

Recalculate using application logic when assumptions change. Do not ask an AI model to perform the authoritative arithmetic.

### 5.5 Community and trader contributions

Future-ready capabilities:
- Community members submit price observations with product, quantity/unit, price, location, time, and optional evidence.
- Participating traders maintain their own listings and update prices/availability.
- Users can flag suspicious or stale reports.
- Moderation and anti-spam protections prevent obvious abuse.

For the hackathon MVP, a simple form to add a price observation is enough if it can be implemented reliably. Do not build a complicated reputation or verification system prematurely.

## 6. AI integration using Meta models

Use Meta models where they provide real value. Check current API access and the exact model names/capabilities before coding.

### Muse Voice Transcribe
Potential use: transcribe a spoken request or voice note. If unavailable, allow text entry as a fallback.

### Muse Spark
Potential use:
- Extract structured shopping items, quantities, budgets, deadlines, destinations, and priorities from natural-language requests.
- Ask a follow-up question when required information is missing or ambiguous.
- Help generate candidate planning preferences.
- Explain the differences between calculated plans in clear, concise language.
- Interpret a user's follow-up such as “I want to spend less on transport even if the shopping bill is slightly higher.”

The model must not invent product prices, availability, opening hours, travel facts, or verified data. It should receive relevant records from the app and refer only to those records when explaining a plan.

### SAM 3.1
Optional later use: support a meaningful image workflow, such as helping identify/segment objects in a submitted product or inventory image, if the API capabilities and licensing/access are appropriate. It is not required for the first MVP.

### Muse Image
Optional later use: generate promotional imagery for participating traders. This is not essential to the core consumer workflow.

### Open-weight models
Muse Glimmer or Muse Spark Open may be considered if their actual availability, licensing, resource requirements, and capabilities fit the project. Do not assume local inference will be practical on low-resource devices.

### Required AI safeguards
- Keep model/API secrets on the server, never embed them in a Flutter client.
- Validate model-produced structured output before using it.
- Treat AI output as a proposal, not a source of truth.
- Use deterministic application code for totals, constraints, and plan scoring.
- Provide a non-AI fallback for creating a list and calculating plans.
- Do not send unnecessary personal information to the model.
- Handle timeouts, rate limits, malformed output, and unavailable APIs gracefully.
- Do not make any plan-changing or external action without user confirmation.

## 7. Decision engine and calculations

Use ordinary application code for all authoritative calculations.

At minimum:
- Line item cost = quantity × unit price.
- Basket cost = sum of eligible line items.
- Total estimated cost = basket cost + transport cost + configured additional expenses.
- Estimated trip duration = estimated travel time + estimated time spent at each stop, accounting for the selected route/order.
- Budget feasibility = total estimated cost <= user budget.
- Deadline feasibility = estimated completion time <= required deadline, where sufficient timing data exists.

A plan should be rejected or marked infeasible if it cannot satisfy a hard constraint. If required information is missing, show that the plan is incomplete rather than inventing the missing value.

Compare plans using user-selected objectives, for example:
- Cost first.
- Time first.
- Fewest stops.
- Balanced cost and time.

If a combined score is used, document its formula and make it understandable. Do not hide important trade-offs behind an unexplained AI score.

For the MVP, a small set of candidate plans can be generated from available sellers and destinations. A sophisticated optimization algorithm is not required initially, but the results must be reproducible and correct for the displayed assumptions.

## 8. Data strategy: simulated data first, real data later

We currently may have no reliable mechanism to collect real local prices. The first version should use a small, consistent demo dataset.

### Demo data requirements
- Use realistic-looking but explicitly fictional sample records.
- Clearly label all simulated data in the UI, including the plan results that depend on it.
- Do not claim that demo sellers are actual businesses. Use names such as “Demo Market A” or clearly fictional seller labels.
- Include product units and quantities so comparisons are fair.
- Use internally consistent prices, transport estimates, opening hours, and travel times.
- Provide enough data to demonstrate several different plans and a scenario where the cheapest individual item choices do not produce the cheapest overall trip.
- Include stale/missing data examples only if the UI explains how they affect recommendations.
- Keep demo data separate from real user-submitted data in the data model and UI.

### Later real-data sources
Potential sources include:
- User-submitted community observations.
- Participating traders.
- Authorized public datasets or APIs, if available and permitted.
- Manual observations gathered by the project team.

Do not scrape websites or use data sources without checking their terms. Never present estimates as actual market observations.

## 9. Suggested core data entities

Adapt these to the selected backend and existing project structure rather than blindly creating a new architecture.

### Product
- id
- name
- category
- standard unit/quantity
- optional description/image

### Seller or location
- id
- display name
- location/coordinates if available
- opening hours and source/status
- seller type (demo, trader, etc.)

### Price observation
- id
- product id
- seller/location id
- price
- quantity/unit
- observed/reported timestamp
- source type
- verification status
- optional submitter id
- optional notes/evidence
- active/stale status

### Shopping list item
- id
- product id
- desired quantity
- priority
- optional acceptable alternatives

### Errand
- id
- title/type
- location
- deadline/preferred time
- estimated service duration
- priority
- completion status
- data/source status for timing or opening hours

### Plan/scenario
- id
- user id, if accounts are implemented
- selected items and errands
- assumptions used
- ordered stops
- estimated product, transport, and additional costs
- estimated duration
- constraints and feasibility status
- calculation timestamp
- data source summary

### User preferences
- currency
- budget defaults
- preferred transport assumptions
- preferred planning objective
- optional saved locations

Use appropriate validation, database constraints, and access rules. Avoid collecting location or personal information that is not needed.

## 10. UI/UX requirements

Build a polished, modern, mobile-first interface suitable for a real consumer product. The design should be clear and purposeful rather than a generic AI dashboard.

Suggested bottom navigation:
1. Home
2. Market
3. Errands
4. Decision Lab
5. Profile/Community (combine or adjust if necessary)

The core workflow should be accessible from Home without forcing users to visit every section.

Important interface requirements:
- Currency displayed clearly, initially Nigerian naira (₦).
- Consistent units and quantities for comparable products.
- Visible labels for simulated, community-reported, and trader-confirmed data.
- Clear timestamps for price observations.
- Accessible text sizes, touch targets, and contrast.
- Useful empty, loading, error, offline, and no-results states.
- Confirmation before deleting lists or discarding a plan.
- Easy editing of AI-extracted items before calculations.
- Explainable recommendations rather than an opaque “AI says so.”
- No fabricated ratings, reviews, savings, live statistics, or business locations.
- Do not overuse charts; tables, cards, comparisons, and concise explanations should serve the task.

## 11. Security, privacy, and reliability

- Never store Meta API keys or other secrets in the client application.
- Validate and sanitize all user input.
- Protect user-submitted data using suitable authentication and authorization.
- Restrict users from modifying other users' private records.
- Rate-limit submissions and model requests as appropriate.
- Provide moderation for reported prices and trader listings.
- Treat user-submitted text and images as untrusted input.
- Keep location collection optional and explain why it is needed.
- Do not expose private user lists or itineraries publicly by default.
- Make external API usage and errors visible in logs without logging secrets.
- Include sensible retry behavior, but avoid duplicate price submissions or duplicate actions.

## 12. Recommended implementation sequence

### Phase 1 — Understand the existing project
Inspect the current repository, framework, existing screens, data model, dependencies, and conventions before changing anything. Reuse existing components and architecture where sensible. Do not replace working code or introduce a new framework without a clear reason.

### Phase 2 — Build the deterministic MVP with demo data
Implement:
- Product and price observation data.
- Shopping list creation and editing.
- Errand creation and editing.
- Basket and total-cost calculations.
- Candidate plan generation.
- Side-by-side plan comparison.
- Scenario controls for budget, transport, time, and stops.
- Explicit demo-data labels.

This phase must work even if Meta APIs are unavailable.

### Phase 3 — Complete the primary end-to-end workflow
Demonstrate a user entering a shopping list, adding a deadline-based errand, viewing candidate plans, changing an assumption, seeing totals recalculate, and accepting a plan.

Test the calculations with known expected results.

### Phase 4 — Integrate Meta AI
Add the appropriate available model to parse natural-language or voice requests and explain calculated alternatives. Keep deterministic validation and calculations in application code. Provide a text/manual fallback.

### Phase 5 — Improve data contribution
Add a form for submitting a price observation, source labels, timestamps, validation, and reporting of stale/suspicious data.

### Phase 6 — Polish the hackathon demonstration
Prepare a reliable demo dataset and a scripted scenario. Make the simulated-data disclosure visible. Test failure cases, loading states, API limits, and all totals. Prepare a concise explanation of how the app uses Meta models.

## 13. Example demo scenario

Use clearly labelled fictional data:

A user has a ₦15,000 budget and needs rice, eggs, tomatoes, and cooking oil. They must also collect a package before 2 PM.

Provide a few fictional sellers with different prices, transport fares, opening times, and travel estimates. Generate several feasible itineraries.

The UI should show:
- Shopping subtotal.
- Transport estimate.
- Total estimated cost.
- Estimated duration.
- Number of stops.
- Whether the package deadline can be met.
- Which prices are simulated.
- Why the recommended plan is preferred.
- How the recommendation changes if the user reduces the budget or increases a transport fare.

Ensure all displayed totals match the underlying calculation exactly. Never label these fictional results as real market data.

## 14. Acceptance criteria

The MVP is ready for demonstration when:
1. A user can create and edit a shopping list.
2. A user can add at least one non-shopping errand with a deadline.
3. Demo price observations are visible and clearly labelled as simulated.
4. The app generates at least two meaningfully different candidate plans when the data permits.
5. Product and transport costs are calculated correctly.
6. The app identifies budget or deadline violations rather than hiding them.
7. Changing an assumption updates the calculated results.
8. The app explains the trade-offs using the actual computed values.
9. The user can accept a plan and mark stops/tasks complete.
10. The core workflow works without a Meta model API connection.
11. API keys and secrets are not present in client-side code.
12. No demo prices, businesses, or observations are misrepresented as real.
13. Loading, error, empty, and missing-data states are handled.
14. The primary demo scenario can be repeated reliably.

## 15. Instructions to the coding agent

Start by inspecting the existing codebase and reporting its current architecture and relevant files. Then implement the MVP incrementally, preserving working functionality.

Do not stop at a plan or mockup: implement the working features, connect the screens to real application state, and verify calculations. Do not build a large set of disconnected screens with fake buttons.

Prioritize the end-to-end workflow over optional features. Do not add unrelated AI chat functionality, decorative dashboards, unsupported live data, or speculative integrations. If a requirement depends on an unavailable API or unclear repository setup, identify the limitation and implement a well-defined fallback.

Before finishing, run the available tests, check for build/runtime errors, verify the sample scenario's arithmetic, and summarize what works, what remains incomplete, how to run the project, and which environment variables (if any) are required.
